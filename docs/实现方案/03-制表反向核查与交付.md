# 第三块：制表、反向核查与交付

日期：2026-10-31；实现更新：2026-11-02。状态：制表、独立验收、反向标注和前端交付入口已实现；真实业务账表及原生 Excel/WPS 效果待验收。

本块对应[整体流程](./00-整体流程.md)第 7—10 步，接收[第一块](./01-数据接入与底稿准备.md)的底稿及来源数据、[第二块](./02-逐行匹配与复核.md)的正式匹配方案，生成文件并完成强制验收。

## 1. 输入、输出和完成含义

输入为同一任务及兼容版本的 `PreparedData`、`MatchPlan` 和人工确认记录。

输出为 `DeliveryResult`，包含 C 表、标注后的 B 表副本、核查报告、统计和交付状态。

业务差异、未匹配和待复核可以如实输出；系统核查未通过时，产物只能作为诊断或待修复文件，不能标记为正式完成。

## 2. 从底稿生成完整 C 表

### 2.1 冻结本次生成的输入版本

验证任务、原始文件内容摘要、字段映射、规则和匹配方案版本，创建新的生成版本。生成期间新增人工确认时，旧产物保留原版本，新方案重新生成。

C 表从 A 完整复制得到的底稿继续加工，不能只拿标准化字段重新拼一张表，导致原始工作簿内容和版式丢失。

### 2.2 按 A 原始顺序写入结果

逐条定位 A 原始明细对应的底稿位置，保留原始业务字段，写入匹配状态、依据、匹配组、复核原因及 B 追溯数据。未匹配和异常 A 行也必须保留。

必须承接的追溯信息：

- B 原始工作表及行号、匹配方向。
- 仓库、系统出入库时间、单据编号、货品编号、货品名称、规格。
- 对应方向的数量、成本单价、成本金额，以及任务中需要保留的固定成本价等附加字段。

追溯字段表头保持与 B 一致；同时需要表达入库和出库时使用明确分区或方向列，不能混用 K—M 与 N—P。

### 2.3 展开匹配关系

| 关系 | C 表写入规则 |
| --- | --- |
| 一对一 | A 原始行承接一条 B 业务记录 |
| 一对多 | 原始行承接第一条，下面逐行展开后续 B 记录，不能只写合计 |
| 多对一 | 保留每条 A 原始业务；同一匹配组的 B 原始追溯记录只完整展示一次，其他 A 行通过组标识关联，分配信息另列或另附明细 |
| 部分匹配 | 保留完整原始值，另列已对应部分和未结余额，不能改写来源值充当分配值 |
| 未确定关系 | 展示 A 行结果和待复核原因，候选可列在复核明细中，不计为已承接 |

一对多附加行中，A 原始业务列保持空白，避免重复计入数量和金额；只填写匹配状态、依据、来源行号、方向及 B 追溯字段。日期上下文可放在追溯信息中，不能把附加行当新增 A 业务。

为每条 B 追溯记录保存稳定来源标识和必要的匹配/分配标识。完整内部标识可放在审计工作表，主表至少要能看到 B 行号、方向和匹配组，便于人和程序共同追溯。

### 2.4 数值、公式与显示

1. A/B 原始数量、单价、金额、成本价和固定成本价按源值承接，不统一四舍五入为两位小数。
2. 原始数值和分配数值分开；不能用重新计算的“数量乘单价”覆盖来源金额。
3. A 明细金额公式优先写入已核实的计算结果，保留原公式来源供审计。缺少结果时按第一块要求重算或待确认。
4. 全部插行后重新定位各合计/小计，按实际业务范围重写公式。多段小计及总计应避免重复累计。
5. 附加行不重复填 A 数量和金额；B 来源及分配的统计也必须区分，避免追溯重复展示导致合计膨胀。
6. 数字优先采用 `General` 等已经验证的格式；整数数量可用 `0`。不使用统一两位小数格式或 `0.###############`。
7. 加宽列宽，检查 `########`、整数尾部小数点和长小数显示。
8. 按状态设置新的颜色和筛选，冻结窗格放在实际表头下方，打开位置复位到 `A1`。

## 3. B 表当月反向核查与标注

### 3.1 从实际 C 表确认承接关系

保存并重新读取 C 表，根据 B 来源标识、方向和原始追溯字段检查实际承接情况。数量、单价、金额按来源精度比较，出库业务按规则比较绝对值。

不能仅凭第二块 `b_usage` 的使用状态认为文件已承接；需检查真实单元格。来源标识相同但数值或追溯字段错误，应报告文件写入错误，不能通过补上“缺失标注”掩盖。

内容相同的 B 行按独立来源身份核对，同时校验数量与重复次数，不能用集合去重后只判断内容出现过一次。

### 3.2 对每条当月记录确定去向

月份范围使用 B 系统出入库时间和任务年月。非本月记录默认不纳入本月缺失统计，跨月追溯需求必须有明确配置和报告说明。

每条当月业务记录归入互斥的一类：

| 去向 | 成立条件 |
| --- | --- |
| 已承接 | 真实 C 表中存在正确追溯数据，原记录对应业务量已完整承接或通过显式分配完整对应 |
| 已标注缺失 | 没有被完整承接，已在 B 副本明确标注缺失、部分未承接或未确定原因 |
| 人工排除 | 存在针对该记录的明确人工排除原因和确认信息 |

入库、出库、零金额、零数量和方向不明的业务均有去向。部分分配不能把剩余数量或金额遗漏掉；记录覆盖与业务量覆盖分别核查。存在未承接余额的记录归入“已标注缺失”，不能又计入“已承接”；其已承接部分和余额在明细中分别列出。

统计同时列出 B 原始行数和按方向拆分的业务记录数，覆盖等式使用同一种业务记录口径：

```text
B 当月业务记录数
  = 已承接业务记录数 + 已标注缺失业务记录数 + 人工排除业务记录数
```

同一原始行同时有入库和出库时分别核查，全部相关方向均有明确去向，该原始行才算去向完整。报告不能把方向记录数冒充原始行数。

### 3.3 生成标注后的 B 副本

在原始 B 副本右侧追加标注，保留原有数据、顺序和来源位置。至少包含：

- C 表缺失标注。
- 缺失类型：入库缺失、出库缺失、零金额缺失、空数量、部分未承接等。
- 缺失方向及具体数量/金额余额（适用时）。
- 缺失匹配依据和标注说明。
- 相关 A/C 行号、匹配组及人工参考表行号（存在时）。
- 人工排除原因及确认引用（适用时）。

缺失行可用浅黄色；标注文字必须说明“本月记录未在 C 表找到”等事实，不能虚构成“人工表有”或把模型判断当作人工确认。

## 4. 独立验收实际产物

生成工具与核查工具职责分离。核查工具重新打开实际输出文件，并独立读取不可变来源及任务期间；不能只验证内存中的计划是否自洽。

| 检查项 | 通过条件 |
| --- | --- |
| A 原始业务完整性 | 原始明细均可对应，数量、单价、金额等原始值未改写，无重复新增业务 |
| A/C 合计 | 重新计算的原始业务数量及金额一致，差额为零 |
| B 追溯完整性 | 行号、方向、仓库、时间、单据、货品及数值与来源一致 |
| B 当月覆盖 | 每条当月记录有且只有一种明确去向，部分匹配余额有说明 |
| 使用与分配 | 无非预期重复承接、重复独占、超量分配或无来源记录 |
| 原始精度 | 超过两位小数的数据未被截断或四舍五入 |
| 合计及公式 | 插行后范围覆盖正确，必要公式已重算且结果正确 |
| 公式错误 | `#REF!`、`#DIV/0!`、`#VALUE!`、`#NAME?`、`#N/A` 等错误数量为零 |
| 显示与视图 | 无 `########` 和整数尾部小数点，列宽可读，视图在顶部，冻结位置正确 |

存在公式并不代表公式已计算。核查需要受支持的重算能力；只有公式字符串或无结果缓存时，相关检查记为未完成，不能宣称通过。

显示检查需使用受支持的渲染或可验证的显示检查能力，抽查整数、长小数和金额列。缺少验证能力时将相应检查明确标为 `not_run`；强制验收项不能用模型的“看起来正常”替代。

## 5. 修复与回流

核查失败应返回结构化问题：`code`、阶段、A/B 标识、输出位置、预期值、实际值及证据引用。

| 问题 | 修复位置 |
| --- | --- |
| 字段映射、日期解析或公式源结果错误 | 第一块修正数据准备，重跑受影响下游 |
| 候选选错、方向错误、重复使用或分配错误 | 第二块修正匹配方案并生成新版本 |
| 插行遗漏、追溯字段写错、合计范围或显示问题 | 第三块修正生成逻辑并重生成 |
| 缺少业务解释或必要确认 | 进入 `needs_input`，保留问题和恢复位置 |

Agent 可以根据问题选择工具和修复阶段。自动修复次数受配置限制，重试耗尽仍未通过时保存失败原因和诊断文件，不改写通过标准。修复后所有受影响文件与检查均需重新执行。

## 6. 结果对象与交付状态

```text
DeliveryResult
  schema_version
  task_id
  data_version
  match_plan_version
  generation_version
  status
  artifacts
  statistics
  verification_report_ref
  review_items_ref
```

每项文件记录类型、文件名、存储引用、内容摘要及版本。核查报告同时提供结构化检查项和可阅读的结论，包含检查状态 `pass / fail / not_run`、期望/实际值、来源及问题位置。

只有强制验收项全部通过后，才把文件注册为最终可交付产物：

- `completed`：验收通过，没有待复核事项；仍需明确列出已解释的业务差异。
- `completed_with_review`：验收通过，存在需要人工继续处理的业务差异或待复核事项。
- `needs_input / failed`：必要确认未完成或强制验收未通过，不发布为已完成结果。

前端按后端实际阶段显示进度，提供 C 表、标注 B 副本及核查报告下载。模型可依据报告生成简明说明，所有数量和结论必须来自实际统计及核查结果。

## 7. 本块完成标准

- C 表来自完整 A 底稿，保持原始业务顺序和数量金额口径。
- 一对多逐条展示 B 明细，附加行不重复 A 原始业务；多对一、部分匹配有清晰关联和分配说明。
- B 当月反向核查实际执行，缺失、排除、零金额及方向分支全部有记录。
- A/C 业务合计、B 覆盖、原始精度、公式及显示检查均有可追溯结果。
- 验收覆盖真实文件，未执行项和失败项不会被当作通过。
- 修复能定位到来源行与对应阶段，重新生成后的版本和下载文件一致。
- 三类最终交付物可下载，待复核业务与系统错误清楚区分。

### 8.1 实际执行链路

```text
校验当前 PreparedData / MatchPlan / 确认历史及文件摘要
  → 冻结数据、匹配和生成版本
  → 从完整 C 底稿生成 C 工作簿
  → 重新打开实际 C，核对真实 B 追溯和分配
  → 由实际 C 事实决定每条 B 的去向
  → 在原始 B 副本追加方向独立的标注
  → 重新打开 C/B，执行全部强制验收
  → 验收失败按问题阶段回流，受限重生成或保留诊断
  → 全部强制项通过后注册 DeliveryResult 和正式下载
```

生成、标注、复验共用第一、第二块任务锁，防止执行中混入人工新匹配版本。发布前再次核对来源和匹配方案；后续人工确认产生新方案时，旧交付下载返回 409，需重新生成。第三块不会擅自修改第一块来源、第二块候选或人工排除原因。

### 8.2 文件及业务口径

- C 来自完整底稿，不重新拼装 A。原始附件、字体/边框及原始二进制资产保留，数值写入不经过浮点重写。
- 一对多在 A 主行后逐条展开 B，附加行全部 A 原业务列为空；多对一和部分共享组只完整展示每条 B 一次，另列每条 A 分配和两侧余额。
- B 追溯表头沿用原 B 文本，入库/出库数值分列，额外保留固定成本价、来源工作表、原行号、方向和稳定匹配组。
- `_对账来源` 保存全部 A/B 的独立来源、原值及原公式；`_对账分配` 保存正式分配边；`_待复核` 展示候选和业务问题，候选不算正式承接。同名原附件不会被覆盖。
- 数量/金额小计及总计按实际业务单元格重写，文本数值使用显式 `VALUE`，嵌套小计不会被再次累计。验收再次展开真实公式依赖，旧范围即使有重新计算的缓存也不能通过。
- 反向核查重新解析 B 原始系统时间。原始行数和方向业务记录数分别统计，双向行在同一 B 来源行中分别标注；部分余额归“已标注缺失”，不重复计入“已承接”。
- 人工排除必须能从实际确认历史重放，包含确认人、业务原因和确认引用。没有对应人工参考表行时，相关标注留空，不编造“人工表有”。
- 原值、精确分配和来源追溯分别验证；真实 C 追溯错误会保留系统问题，不能通过 B 缺失标注掩盖。

### 8.3 当前明确支持的验收能力

公式引擎标识为 `exact-formulas-v1`。支持有限十进制的加减乘除、普通跨表单元格引用、`SUM`、`VALUE`、`SUBTOTAL(9/109)`；共享公式先在原坐标展开。生成时写入重新计算的结果缓存，验收时再次从实际单元格计算并比较缓存；缺缓存和错误缓存均不通过。

**这不是完整 Excel/WPS 计算引擎。** 未支持函数、数组/数据表公式、外部或结构化引用等会记录 `not_run` 或明确计算问题，不凭公式字符串或旧缓存登记完成。无限循环小数结果不会静默截断为可交付值。

显示能力标识为 `ooxml-display-bounds-v1`，是可验证的格式、尺寸及视图边界检查，**不宣称已由 Excel/WPS 实机渲染**：

- 数字限于已验证的 `General`、整数 `0` 和固定日期时间格式，列宽按内容、东亚宽字符及字号保守设置。
- 检查数字宽度、文本换行与行高、隐藏状态、井号/整数尾点、真实表头冻结和 `A1` 打开位置。
- 对日期序列保留来源值，并以日期时间格式显示。一般金融数值超过 15 位有效数字时，仍保留源值，但显示检查记为未完成，不通过截断换取验收。
- 原生表格、绘图/嵌入显示对象、扩展显示、未知字体/格式或超过尺寸边界的内容，当前能力无法证实其最终显示，明确 `not_run`，需补充受支持的渲染/重算适配器后验收。

请求中可显式关闭公式或显示能力以验证门槛；任何强制项 `fail/not_run` 均不会注册正式交付。报告同时记录实际能力标识和限制。

### 8.4 HTTP、版本及恢复

接口前缀：`/api/delivery/tasks/{task_id}`，沿用第一、第二块编号。

| 方法及后缀 | 功能 |
| --- | --- |
| `POST /run` | 按预期匹配版本生成或恢复；同输入已完成任务幂等返回，`force=true` 生成新版本 |
| `GET`（无后缀） | 实际阶段、尝试次数、UTC 时间线、系统问题及当前版本 |
| `GET /result?expected_generation_version=N` | 当前交付对象、实际统计及带摘要文件清单 |
| `GET /report?expected_generation_version=N` | 实际 C/B 的结构化强制验收报告 |
| `POST /verify?expected_generation_version=N` | 重新打开已登记文件复验；修改、损坏或丢失立即撤销正式下载资格 |
| `GET /artifacts/{name}?expected_generation_version=N` | 只下载当前已通过验收的正式文件 |
| `GET /diagnostics/{name}?expected_generation_version=N` | 明确标记的诊断工作簿及报告，不代表正式完成 |

最小启动请求：

```json
{"expected_match_plan_version": 2}
```

可选 `options`：`max_auto_repairs`（默认 1，0—3）、`formula_engine`（`builtin/unavailable`）、`display_engine`（`bounds/unavailable`）；`force` 默认 false。强制验证能力不可用不会被模型判断替代。

任务原子头保存为 `delivery/state.json`。工具中断后 `/run` 对同一冻结版本恢复，重新从底稿执行可重放的生成流程，避免在旧 C 上重复插行。每轮从实际文件重新验收；修复预算耗尽后保留诊断及问题，不改变通过标准。

`completed` 与 `completed_with_review` 都要求实际文件的所有强制项通过；后者保留真实业务差异或待复核。`needs_input/failed` 的文件仅从诊断入口下载。下载检查生成版本、最新匹配版本及实际 SHA-256；文件登记后被修改也不能继续下载为正式结果。
