# 第二块：逐行匹配与复核

日期：2026-10-31。状态：实现规划。

本块对应[整体流程](./00-整体流程.md)第 5—6 步，接收[第一块](./01-数据接入与底稿准备.md)的数据包，以 A 原始明细为主线确定匹配关系，交给[第三块](./03-制表反向核查与交付.md)生成和验收文件。

## 1. 输入、输出和边界

输入为 `readiness=ready` 的 `PreparedData`，以及后续追加的人工确认、别名和排除原因。

输出为 `MatchPlan`：包含每条 A 明细的处理结果、已校验匹配组、B 记录使用关系、复核事项和业务排除记录。

本块处理匹配关系，不在遍历过程中直接插入 C 表行。每条 A 明细均进入 Agent 工作流，模型只在需要语义理解或判断的环节调用。

## 2. 逐行处理流程

### 2.1 初始化任务和记录状态

验证数据包、字段映射和规则版本，按 A 原始顺序建立处理队列，并载入 B 索引、人工确认和已有进度。

每条 A 明细必须有结果。标题、小计、合计等非业务行已由第一块识别并保留在底稿中，不作为本块的匹配对象。

先通过严格规则寻找明确关系，再对遗留行执行更宽松的检索和语义分析。可以回访已处理行；A 顺序是处理主线，不是“先找到就永久占用 B 记录”的规则。

### 2.2 读取当前 A 行及上下文

程序向当前行任务提供：

- A 原始记录标识、原始值及标准化字段。
- 所属日期组、单据组、相关备注和必要的相邻明细。
- 匹配规则、字段可用情况、已有问题和人工确认。
- 与该行相关的候选及 B 记录使用情况。

数字缺失、解析失败和零值分开处理。无法计算的行形成明确问题，不能编造金额或把错误值当零继续匹配。

### 2.3 确定业务方向

| A 行情况 | B 候选范围 | 处理要求 |
| --- | --- | --- |
| 数量为正 | 入库 K—M | 保留入库方向和原始追溯值 |
| 数量为负 | 出库 N—P | 数量及对应金额按规则比较绝对值，A 原始负数不改写 |
| 数量为零、金额为零或补发件 | 按单据、货号、仓库、备注等查找 | 不自动跳过；证据不足时标记零金额或补发件需复核 |
| 方向不明或字段异常 | 保留记录并检查上下文 | 无法确定时保存异常或待确认原因 |

零金额并不必然意味着数量为零。数量、金额符号冲突等情况必须记录，不能只凭其中一个字段强行判断全部业务。

### 2.4 程序生成并检查候选

从严格到宽松逐层检索：

1. 同日期、同货号/规格、数量及相关数值条件一致的单行。
2. 同单据或同货号、同规格、同系统日期的多行组合，包含连续与非连续记录。
3. 在已明确的日期范围内，数量和单价等支持对应关系、但日期或规格需要复核的组合。
4. 结合相关 A 行检查多对一或部分匹配关系，保存分配及未结余额。

组合计算由程序完成。先按单据、货号、规格、方向、单位和日期等缩小范围，不能只凭数量相加相等就认定匹配。不同商品、不同单位或方向冲突的记录不能任意拼合。

每个候选保存原始记录引用、规则编号、数量/单价/金额/日期等检查结果和差异。金额差异需要如实记录，不能通过改写 A/B 原值或统一四舍五入消除。

日期容差、别名及数值比较口径来自版本化规则。未配置的数值容差不得擅自采用；部分匹配保持独立状态，不能标成普通已匹配或仅日期/规格需复核。

组合搜索需要有执行预算和可恢复状态。达到预算上限时返回 `search_incomplete`，保留未完成范围并转复核或补充搜索，不能把未搜索完等同于“没有对应记录”。

### 2.5 对疑难项调用模型

以下情形可以调用模型：

- A/B 产品或规格可能为简称、别名、符号或后缀差异。
- 日期不同，但单据、货号及数值存在对应依据。
- 有多个通过数值检查的候选，需要结合上下文比较。
- 当前检索无明确结果，需要提出新的别名或查询条件。

模型接收当前 A 行、必要上下文、候选标识及程序检查结果，返回结构化建议和证据。模型可以建议继续调用检索工具、采用候选并标复核、或保留未确定结果。

模型不能创造不存在的 B 行、修改源值、替代数量计算或自动生成业务排除。新别名先作为当前任务的建议，不直接写成所有任务共用的已确认映射。

每行的模型轮次和工具查询次数应受任务配置限制。超过限制保留完整进度和问题，进入可复核状态。

### 2.6 保存当前行结果

程序检查建议涉及的记录存在、方向正确、数值条件成立、引用版本一致，并检查是否与其他匹配冲突。

| 状态 | 含义 |
| --- | --- |
| `matched` | 通过明确规则且没有待复核差异 |
| `matched_review` | 对应关系有足够数值和业务依据，但日期/规格等仍需复核 |
| `partial` | 仅有部分数量或金额对应，保存已对应部分和余额 |
| `unmatched` | 在已完成的规则搜索中没有确定对应关系 |
| `unresolved` | 候选有歧义、搜索未完成或证据不足，等待后续处理或人工复核 |
| `anomaly` | 数值、方向、重复使用等存在明确异常 |

`matched_review` 必须有具体对应关系和检查证据。多个候选无法确定时使用 `unresolved`，候选引用与正式匹配引用分开保存，不能把所有候选都写成已承接。

行处理阶段的 `pending` 和执行失败单独记录，不能冒充业务 `unmatched`。已识别的业务异常可以如实进入结果；文件读取失败或必要数值无法获得等阻塞需先解决。

## 3. 整表关系检查与人工复核

逐行结果形成后，检查全局关系：

1. 不同 A 行是否竞争同一 B 记录。
2. 同一业务组是否需要重新组合。
3. 一对多、多对一及部分匹配的分配总量是否超过原始业务量。
4. A 每条明细是否有唯一行结果，B 的使用关系是否与正式匹配一致。
5. 人工修改是否使其他行已有关系失效。

明确匹配与暂定候选分开管理。多对一和部分匹配通过显式分配记录共享 B 业务量，不能让多个行任务分别把同一 B 记录当作完整独占记录。共享同一 B 记录的相关 A 行归入统一匹配组，供第三块集中展示原始追溯信息和分配明细。

对于无法自动消除的歧义，保存候选、原因和人工处理入口。人工确认记录应包含对象、选择、确认人和时间；排除 B 记录还必须包含业务原因。人工确认也不能绕过来源精度、数量分配和重复使用检查。

人工答复会产生新的匹配方案版本，重新计算受影响的行和 B 使用状态。第三块不得使用旧版本生成“最新结果”。

## 4. 数据交接约定

基础来源和数值结构沿用第一块，本块新增以下对象。

### 4.1 候选与模型建议

| 对象 | 主要字段 |
| --- | --- |
| 候选 `Candidate` | `candidate_id`、A/B 记录标识、规则、检查结果、差异、来源及搜索状态 |
| 模型建议 `ModelProposal` | 关联候选、新查询建议、规格关系判断、理由、证据引用及复核要求 |
| A 行结果 `ARowResult` | A 标识、处理状态、正式匹配组、独立的候选引用、原因和处理日志引用 |

例：A 数量 462，B 两条候选数量分别为 449、13。程序先验证数量合计以及方向、单价等条件；模型只分析“站脚款”和“站脚”的名称差异。建议经过校验后，可形成带规格复核要求的一对多关系。

### 4.2 匹配组 `MatchGroup`

| 字段 | 含义 |
| --- | --- |
| `group_id` | 稳定匹配组标识 |
| `a_record_ids`、`b_record_ids` | 组内正式对应的 A/B 业务记录 |
| `relation_type` | `one_to_one / one_to_many / many_to_one / partial` |
| `direction` | 入库、出库或明确的待复核方向 |
| `allocations` | A/B 对应的数量或金额分配；分配值与源值分开 |
| `checks`、`rule_id` | 程序检查结果及使用规则 |
| `status`、`review_reasons` | 正式状态和需要复核的具体原因 |
| `evidence`、`confirmation_refs` | 可追溯依据和人工确认引用 |

本方案不要求通过拆分或分配改变 B 表原始数量、单价、金额。原始追溯数据保持原样，分配信息另存，生成文件时明确区分。

### 4.3 匹配结果 `MatchPlan`

```text
MatchPlan
  schema_version
  task_id
  prepared_data_ref
  rule_version
  match_plan_version
  a_row_results_ref
  match_groups_ref
  b_usage_ref
  review_items_ref
  exclusions_ref
  execution_issues_ref
  readiness
```

`b_usage` 从正式匹配组及分配关系推导，与匹配方案一致更新，不能单独手改形成另一套事实。未采用的候选不构成正式使用，缺失标注由第三块核对实际产物后生成。

`readiness` 使用 `ready / needs_input / failed`。`readiness=ready` 表示可以如实制表，不表示全部业务已经匹配。所有 A 行必须有明确业务结果，阻塞性执行问题已解决，竞争关系没有被伪装为已确定匹配。未确定候选可作为复核事项输出。

## 5. 工具与恢复要求

建议程序工具包括：读取行上下文、查询 B 候选、搜索组合、检查候选、保存建议、检查冲突、提交匹配组及记录人工确认。

模型提交的结果必须经过程序验证工具才能成为正式关系。工具返回结构化状态、差异、来源引用和错误码，不依赖自然语言一句“匹配成功”驱动后续制表。

每条 A 行处理及匹配组提交应可重复执行，恢复任务不能重复追加或重复消耗 B 记录。候选暂定、释放和正式提交需保持一致，发生异常时恢复到可解释的状态。

第三块发现缺失承接、重复使用或方向错误时，携带 A/B 标识和错误码回到本块修复；新方案重新生成受影响文件并验收。

## 6. 本块完成标准

- 所有 A 原始明细均有处理结果，无静默遗漏。
- 严格单行匹配无需逐行调用模型，疑难行的模型输入输出可追溯。
- 正数入库、负数出库及绝对值比较正确，零金额与补发件保留。
- 支持非连续多行组合，搜索不完整有独立状态。
- 日期/规格复核具备实际依据，数量或金额不符不能伪装成普通已匹配。
- 一对多、多对一及部分匹配有明确关系和分配，不超量、不重复独占。
- 完全相同内容的 B 来源行仍可独立匹配和计数。
- 冲突、人工确认、规则变化和断点续跑不会产生重复关系。
- `MatchPlan` 可由第三块独立加载，包含制表所需的全部正式关系和复核信息。
