## 2. 项目目标与业务口径

项目名称为“清账”，目标是以业务底稿 A 表为基础，承接系统出入库 B 表，生成可追溯、可人工复核并通过双向核查的 C 表。

### 输入

- A 表：客户、供应商或业务侧提供的对账底稿，决定原始业务内容、顺序和基本版式。
- B 表：系统出入库明细，包含仓库、系统时间、单据、货品、规格及入库/出库数值。
- 对账年月：明确到年和月，用于 B 表当月反向核查。
- 可选输入：字段映射、名称映射、日期容差、人工调整参考表和人工确认结果。

### 最终目标输出

1. 完整 C 对账工作簿。
2. 带当月缺失、排除等标注的 B 表副本。
3. 核查报告和待复核事项。

当前第一块只完成上述最终流程的数据准备。正式匹配、B 表缺失标注及交付验收需要后两块继续实现。

### 已确定的业务约束

- 以 A 原始明细为处理主线，每行均有明确处理结果；必要疑点才调用大模型。
- 原始输入保持可追溯，标准化值与原值分开。
- A 正数匹配 B 入库，A 负数匹配 B 出库，比较时正确处理绝对值。
- 零数量、零金额、补发件及退货不能自动忽略。
- 支持连续及非连续多行组合；匹配关系先保存，C 表最后统一展开。
- 数量、单价、金额及成本价保留来源精度，不统一改成两位小数。
- B 当月记录必须被承接、标注缺失或有明确人工排除原因。
- A/C 原始数量、金额差额为零，实际文件通过核查后才能登记最终完成。

这些约束覆盖三块整体目标，并不表示对应能力均已实现。

## 4. 第一块已完成的实现

### 4.1 技术及项目结构

后端使用 Python 3.13+、FastAPI、LangGraph、Pydantic、Decimal 和本地文件仓库。

核心代码位于 [backend/app/preparation](../backend/app/preparation/)，职责分为：

| 层/目录 | 职责 |
| --- | --- |
| `domain` | 不可变数据契约、状态及字段枚举、来源值与业务错误 |
| `ports.py` | 工作簿适配器及模型建议的类型化接口 |
| `application` | 字段识别、标准化、索引、任务状态和阶段用例 |
| `workflow` | LangGraph 节点、路由、中断及恢复 |
| `infrastructure` | 文件存储、OOXML 适配及模型服务调用 |
| `prompts` | 独立提示词文案、装配、版本和内容摘要 |
| `app/api/v1/preparation.py` | 上传、查询、确认、续跑及下载接口 |

开发约束沿用本对话要求：把 Python 按强类型方式开发，函数参数及返回值带类型注解，函数说明写清作用、参数含义与输出含义。已启用 `mypy strict`，并用代码契约测试检查新生产函数的注解和说明。

### 4.2 实际处理链路

```text
接收 A/B 及可选人工参考表
  → 保存原文件、任务编号和文件摘要
  → 解析工作簿快照及有限结构摘要
  → 已知表头规则识别；必要时调用模型提出映射
  → 程序验证字段、范围和年月
  → 标准化 A/B 明细并计算 A 业务合计
  → 完整复制 A 并加工为 C 初始底稿
  → 保存 B 查询索引、审计及 PreparedData
  → 第一块 ready
```

必要信息不足时进入 `needs_input`，由 LangGraph `interrupt` 暂停。补充后使用 `Command(resume=...)` 恢复；输入变化增加数据版本，确认内容及时间留审计。

### 4.3 已有能力

- 原生接收 `.xlsx`，校验实际大小、文件结构及角色。
- 保存原文件、SHA-256、任务及版本信息。
- 读取单元格原值、公式缓存、工作表、合并区域、样式及隐藏行列等结构。
- 支持规则字段识别、可选模型建议、人工映射及程序校验。
- 只在原合并日期范围内补全日期，支持 1900/1904 日期系统及常见文本日期。
- A 明细保持原始顺序，标题、重复表头、小计和合计不重复计入业务合计。
- 使用 Decimal 计算；结构化数值按十进制文本交接，避免浮点重写来源数值。
- B 按入库、出库或未知方向保留记录，重复内容保留独立来源身份，跨月数据不提前丢弃。
- C 底稿保留原工作簿部件和附件表，处理合并、静态底色、日期显示及数值格式。
- A 必要数值公式承接已有缓存或经人工核实的结果；缺少结果时暂停，不按零处理。
- 保存 B 查询索引、A 基准合计、清理审计和确认历史。
- 提供任务排他锁、幂等执行、版本冲突检查及进程重启后的检查点恢复。

## 5. AI 与提示词的当前状态

AI 接入方式是“规则优先、必要时模型辅助识别”。程序已获得明确字段映射时直接继续；存在未确定映射且已配置模型时，调用 `StructuredMappingAdvisor`。

模型输入为 `TableProfiles`，包含表头、合并范围及有限样例；输出协议为 `MappingAdvice`。模型建议仍需经过字段、范围、来源和数值处理校验。

提示词现已独立管理：

- [系统提示词](../backend/app/preparation/prompts/templates/field_mapping_system.md)：角色、规则、数据边界和输出要求。
- [用户提示词](../backend/app/preparation/prompts/templates/field_mapping_user.md)：输入说明及 `${profiles_json}` 变量。
- [版本及构建入口](../backend/app/preparation/prompts/field_mapping.py)：`preparation.field_mapping`，当前版本 `1.0.0`。
- [维护说明](../backend/app/preparation/prompts/README.md)：变量、编辑、版本、追踪和扩展约定。

每次模型调用 metadata 带提示词标识、版本和模板 SHA-256。模板缺失、变量契约或语法错误会明确失败；输入 JSON 内的类似占位符文字不会二次替换。当前 metadata 用于调用追踪，没有另行写入任务的 `mapping_advice.json`。

## 6. SQLite 使用原因与存储分工

已阅读 [查找 SQLite 的使用原因](codex://threads/01a19a28-2774-7d83-b00d-e1d06fca6712) 对话，并与当前代码交叉核对。

### 当前用途

SQLite 用于 LangGraph **持久化执行检查点**，支持等待人工补充、记录执行位置和中断信息、后端重启后续跑。每个任务目录下保存独立 `checkpoints.sqlite`。

例如，任务缺少月份时先中断，用户补充月份后恢复；期间重启服务，仍可凭同一任务编号找到原检查点。

| 存储 | 当前保存内容 |
| --- | --- |
| `checkpoints.sqlite` | LangGraph 内部执行检查点、中断及恢复信息 |
| `task.json` 和版本 JSON | 任务状态、配置、原始快照、标准化明细、索引、审计及确认记录 |
| Excel 文件 | 原始 A/B/人工参考表及生成的 C 初始底稿 |

图的自定义业务状态仅包含 `task_id`、`data_version`，整张工作簿和全部明细由文件仓库持有。实现见 [任务执行服务](../backend/app/preparation/application/service.py) 和 [图状态及节点](../backend/app/preparation/workflow/graph.py)。

### 当前架构结论

- 当前采用 SQLite，可以随任务目录保存检查点，无需另行部署检查点数据库服务。
- 需要保留的是“可持久化、可恢复的检查点能力”；SQLite 是现阶段实现方式。
- 上述对话说明了选型用途，未提出迁移数据库或删除 SQLite 的实施决定。
- 未来若需要多实例共享执行状态，再评估集中式检查点存储；该项不计入已实现能力。

`ready` 的准确含义是：**输入已整理到可以进入第二块匹配的状态。** 它不证明 A/B 已完成业务匹配，也不替代最终文件的强制验收。
